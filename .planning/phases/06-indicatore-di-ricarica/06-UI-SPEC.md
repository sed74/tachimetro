# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** Tachimetro is a native Android app (Kotlin, XML layouts, ConstraintLayout, no Jetpack Compose, no npm/shadcn). This contract adapts web-oriented template concepts to Android idioms: "px" → dp/sp, "component registry" → Android resource files (`colors.xml`, drawable XML, layout XML), "hover/focus states" → visibility/animation states driven by battery broadcast.

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from existing app-wide usage, confirmed in `activity_main.xml`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4dp | not used this phase |
| sm | 8dp | Gap between charging icon and `keepScreenOnSwitch` (icon sits to its left, per D-06) |
| md | 16dp | Base start/bottom margin for the bottom-left corner group (icon becomes the new leftmost element, inherits the existing `16dp` base margin previously on the switch) |
| lg | 24dp | Charging icon fixed size (width = height = 24dp — standard Material icon grid, a clean multiple of 4/8) |
| xl | 32dp | not used this phase |
| 2xl | 48dp | not used this phase (icon is decorative/non-interactive, see below) |
| 3xl | 64dp | not used this phase |

Exceptions:
- The charging icon is **non-interactive** (no click target, no state change on tap — it is a passive status indicator). The existing 44/48dp minimum touch-target rule (already applied to `keepScreenOnSwitch`, `resetMaxButton` via `minHeight="48dp"`) does **not** apply to this icon. Set `clickable="false"` / `focusable="false"` on the `ImageView`.
- Icon size (24dp) is fixed, not resizable by autosize — this is the only new component this phase and it does not scale with the speed digits' autosize system.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FF000000` (`@android:color/black`) | Full-screen background — unchanged |
| Secondary (30%) | `#FFFFFFFF` (`@android:color/white`) | All existing text, the switch's off-state track/thumb tint, and the charging icon's **base/empty** color (the "white" ends of the "bianco → lime → bianco" cycle) — unchanged |
| Accent (10%) | `#FFAEEA00` (Material "Lime A700") — **new**, add to `colors.xml` as `lime_charging_accent` | Reserved **exclusively** for the charging indicator icon's animated fill (both the pulsing loop and the static full-charge state) |
| Destructive | not applicable this phase | The existing "Azzera massimo" button (Phase 4) is unstyled/default and out of scope for Phase 6 — no destructive action is introduced here |

Accent reserved for: **the charging icon's fill color only** — the bottom-to-top rising fill during active charging, and the fully-solid fill when the battery reaches `BATTERY_STATUS_FULL` while still connected (D-03). Never applied to: switch thumb/track, button backgrounds, any text, the app background, or any other icon. This is the app's single explicit exception to its otherwise strict black/white palette (PROJECT.md Constraints, D-04) — the checker should flag any lime usage found outside this one icon as a violation.

Color value rationale (resolved from CONTEXT.md "Claude's Discretion — esatto valore del colore lime"): Material Design "Lime A700" (`#AEEA00`) chosen over the more neon `#C6FF00` (Lime A400) for a vivid but slightly less yellow-shifted lime that reads clearly as "lime" (not "warning yellow") against a pure-black background, at high contrast for glance-legibility in bright daylight (core value alignment). This is a locked default, not a question requiring further confirmation.

Accessibility note: color alone is not the only signal — icon presence/absence (charging vs. not) and fill-shape state (pulsing vs. solid-full) are also visually distinct, so the indicator remains legible for color-vision-deficient users even though lime/white contrast is the primary cue.

## Component & Interaction Spec — Charging Indicator

*(Native-Android equivalent of the template's "Visuals" dimension — component inventory, layout, and state machine for the one new UI element this phase introduces.)*

### New Android resources

| Resource | Name | Notes |
|----------|------|-------|
| Color | `res/values/colors.xml` → `lime_charging_accent` = `#FFAEEA00` | See Color section above |
| Drawable | `res/drawable/ic_charging_flash.xml` | Stock Material "flash on" bolt glyph, 24x24dp viewport, sourced via Vector Asset Studio (D-05: classic solid zigzag, not a thin/outline custom design) |
| View | `chargingIcon` (`ImageView`, id `@+id/chargingIcon`) in `activity_main.xml` | New element in the existing `ConstraintLayout` |
| String (optional) | `charging_indicator_description` = `"In carica"` | Only if the accessibility content-description default above is adopted |

### Layout / positioning

- `chargingIcon`: 24dp × 24dp, `ImageView`, `clickable="false"`, `focusable="false"`.
- Constraints: `layout_constraintStart_toStartOf="parent"` (same base `16dp` start margin `keepScreenOnSwitch` currently has), `layout_constraintTop_toTopOf="@id/keepScreenOnSwitch"`, `layout_constraintBottom_toBottomOf="@id/keepScreenOnSwitch"` (vertically centered against the switch row, per D-06 "sulla stessa riga orizzontale").
- `keepScreenOnSwitch` constraint change: `layout_constraintStart_toStartOf="parent"` → `layout_constraintStart_toEndOf="@id/chargingIcon"` with `layout_marginStart="8dp"` (the `sm` token — gap between icon and switch).
- **Window insets (critical — do not skip):** `chargingIcon` becomes the new leftmost element in the bottom-left corner group, taking over the role `keepScreenOnSwitch` currently plays in `applyScreenSwitchWindowInsets()` (`MainActivity.kt:435-450`). The live `systemBars`/`displayCutout` bottom+left inset must be applied to `chargingIcon`'s base margins (not the switch's, since the switch's start constraint now chains from the icon rather than from parent). Follow the same pattern already used for `applyMaxAreaWindowInsets()` (label + button chained inset) — do not reuse the switch's existing listener instance as-is; extend/replace it so both `chargingIcon` and `keepScreenOnSwitch` end up correctly positioned in both orientations.
- Single adaptive layout only (no `layout-land` variant) — consistent with the Phase 3 decision; the icon inherits this automatically since it is constrained relative to the switch, not to fixed screen coordinates.

### States

| State | Trigger | Visual |
|-------|---------|--------|
| Hidden | Not connected to power (`BATTERY_STATUS_DISCHARGING`/`NOT_CHARGING`/`UNKNOWN`) | `chargingIcon.visibility = View.GONE`. No placeholder, no fade — instant toggle (see Transitions below). |
| Charging (pulsing) | `BATTERY_STATUS_CHARGING` | `View.VISIBLE`. Continuous bottom-to-top fill animation loops indefinitely (see Animation spec below). |
| Charging complete (solid) | `BATTERY_STATUS_FULL` while still connected | `View.VISIBLE`, animation stopped/frozen at 100% fill — icon renders fully solid lime, no motion (D-03). |
| Resumed charging after full | State transitions back from `FULL` to `CHARGING` (e.g. trickle recharge) while still connected | Pulsing animation restarts from 0% (empty/white) — per D-03 "torna a pulsare... se lo stato cambia di nuovo." |

### Transitions

- **Appear/disappear:** instant `View.VISIBLE` ↔ `View.GONE` toggle, **no fade/slide/crossfade**. This matches the existing `updateMaxArea()` pattern ("Plain visibility toggle, no animation") and the explicit project-wide constraint that the fill animation is the *only* animation permitted anywhere in the UI (D-04, PROJECT.md Constraints).
- **Unplug during an active fill cycle:** icon disappears **immediately**, regardless of animation phase — do not wait for the current loop iteration to complete (roadmap SC2: "scompare immediatamente").
- **Re-plug:** pulsing animation always restarts fresh at 0% (empty/white), never resumes mid-cycle from a cached phase.

### Animation spec (fill loop)

- **Direction:** bottom-to-top progressive fill, like liquid rising inside the bolt silhouette — not a flat crossfade/tint change (per user's explicit description in `06-CONTEXT.md` "Specific Ideas").
- **Color cycle:** white (`@android:color/white`, 0% filled) → lime (`lime_charging_accent`, 100% filled) → white (0% filled again) — one full white→lime→white cycle = one loop iteration.
- **Cycle duration:** 2500ms total per loop (fill 0%→100% in 1250ms, drain 100%→0% in 1250ms), matching the "~2-3 secondi" requirement (CHRG-02) with a concrete, implementable number.
- **Interpolator:** accelerate-decelerate (ease-in-out) for both the fill and drain halves — avoid a linear/robotic interpolator, which reads as mechanical rather than liquid-like.
- **Loop:** infinite repeat while in the "Charging (pulsing)" state; cancelled/frozen (not paused) when transitioning to "Charging complete" or "Hidden".
- **Recommended implementation approach (non-binding — technical mechanism remains Claude's/executor's discretion per `06-CONTEXT.md`):** a `ClipDrawable` (`android:clipOrientation="vertical"`, `android:gravity="bottom"`) wrapping a lime-colored copy of `ic_charging_flash.xml`, layered over a white base copy, driven by a single `ValueAnimator` (0–10000 level, `REVERSE` repeat mode, 2500ms duration) — or an equivalent `AnimatedVectorDrawable`. Either is acceptable; the **visual result** described above is the binding contract, not the mechanism.
